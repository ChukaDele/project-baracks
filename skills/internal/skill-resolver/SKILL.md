# Skill Resolver

Installed does not mean loaded.

## Resolve before acting

For substantive work:

1. classify the task by outcome, source type, risk, uncertainty and execution mode;
2. identify the smallest set of skills whose descriptions/triggers directly match;
3. load those skills before inventing a new process;
4. prefer the more specific skill when two overlap;
5. compose skills only when each adds a distinct capability;
6. do not load a broad skill merely because it is adjacent to the topic.

## Positive/negative trigger discipline

When a skill provides resolver examples, compare the current task against both:

- **should trigger** examples;
- **should not trigger** examples.

A near-neighbour negative example is strong evidence not to load the skill.

## Reachability audit

When adding or reviewing skills, flag:

- a useful skill that no realistic task can trigger;
- duplicate skills that compete for the same task;
- one broad skill that shadows a more specific skill;
- obsolete skills still present after a replacement;
- trigger language that is so vague it loads on most work.

## Escalation

If no existing skill fits:

- solve the real task first using normal reasoning/tools;
- if the successful procedure is reusable, run `skillify` afterward.

Do not create a new skill as a substitute for finishing the current outcome.
